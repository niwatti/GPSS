# 性能問題の調査と改善設計

更新: 2026-11-01。対象はM6実装と後続のR1〜R3最適化。報告条件は**XInput・通常モード・1,000Hz、約10秒で表示が重くなる**。この文書は原因調査・改善仕様の正本である。R1〜R3は実装済み、R4計測機構とmacOS上のモック/仮想負荷を実施済み。Windows WPFの性能受入は未完了。実装・最新検証結果は[09-performance-implementation.md](09-performance-implementation.md)。

## 結論と確度

優先して直すのは、30秒窓を毎回全件コピー・再集計する解析経路と、同じ解析結果を約60回/秒再描画するUI経路である。M6の「解析p95<100ms」と「最終ヒープが一定」だけでは、表示性能の合格条件として不十分だった。

| 判断 | 根拠 | 確度 |
| --- | --- | --- |
| 解析の割当量・GC負担が、開始から30秒まで増える | 全件コピー/全件再計算のコードと、処理別・実時間モックの計測 | 確認済み |
| 同じ統計・波形にも頻繁な文字列生成と描画要求がある | UIの17msタイマー、無条件のRender/InvalidateVisual | コードで確認済み。Windows上の時間は未計測 |
| 両者のCPU/GC/Dispatcher負荷が実機の重さに寄与する | 報告の時間依存性と一致する構造、モックでのGC停止増加 | 有力な原因。実機での寄与率と完全な因果確定にはWindowsプロファイルが必要 |
| 履歴が無制限に増えるメモリリーク | 窓/キュー/描画点に上限があり、M6のライブヒープは概ね安定 | 今回の調査では根拠なし。Windowsのネイティブ資源は別途確認 |

ユーザーの1,000Hzが「API呼出し/秒」か「状態更新検出/秒」かは未確定。XInputはpacket更新時だけ記録するため、再現記録には両方と軸別件数を残す。通常モードのまま改善し、取得方式・計測意味を変更する前提にはしない。

## 確認した処理

ソース位置はM6時点のもの。後続修正では行番号よりクラス/メソッド名を基準に追跡する。

| 処理 | ソース | 問題 |
| --- | --- | --- |
| 毎100msの4軸解析 | `GpssController.ProcessOnce`（Application、約198〜215行） | snapshot、描画縮約、最頻推定、震え、1秒レートを毎回全件から計算。解析とキュー取り込みが同じworkerなので、重い計算中はキュー消費・現在位置公開も遅れる |
| 全窓コピーと差分再生成 | `AxisWindow.Snapshot`（Core、約82〜99行） | Queue→LINQ→immutable配列、差分builder→配列を繰り返し生成。表示側への点数制限は、このコピーを抑制していない |
| 震え再計算 | `JitterCalculator.Calculate`（Core、約5〜16行） | 値配列・平均からの偏差配列を生成し、複数回走査 |
| 最頻差分 | `ModalStepEstimator.Estimate`（Core、約54〜102行） | 毎回DictionaryとバケットごとのListを作成し、差分を全保存。勝者配列を作り、最頻バケット内の値もSort。差分種類が多い系列ほど負担増 |
| 実測レート | `GpssController.ProcessOnce`（約208行） | 最新1秒のためにも30秒分を走査し、新しい配列を生成 |
| 全UI更新 | `MainWindow`（Desktop、19/77/123〜139行）、`StickPanel.Render` | 約58.8回/秒で位置・統計・詳細・経過時間を同時に更新。折りたたんだ詳細も文字列を作る |
| グラフ描画 | `HistoryControl.HistoryPlot.Set/OnRender`（約75〜124行） | Setは同じ窓でもInvalidateVisual。点列の間引きだけ10Hzにしており、描画命令・目盛・文字の生成は再描画ごと |

UIの通常時は1 tickあたり17個のTextBlockへ代入するコード経路があり、4グラフへ再描画要求を出す。名目上は約1,000回/秒の文字代入と約235回/秒のグラフ無効化になる。同じ文字列の代入がすべて再レイアウトを起こすとは断定しないが、文字列の整形処理自体は実行される。

各グラフのOnRenderは目盛等のFormattedTextを11個生成し、Pen/Brush/Typefaceも繰り返し生成する。線分は間引き後の点ごとにDrawLine/DrawEllipse。8192点/軸の上限を使う保守的な上限では4軸×8192点×58.8回≒193万点分の命令/秒になり得る。実際の点数・描画回数は幅、入力、WPFの要求統合等で変わるため、これは実測ではない。

最初の30秒は `N ≈ 軸の観測/秒 × 経過秒` で処理対象が増える。1k観測/秒なら10秒で約1万点/軸、30秒で約3万点/軸。AxisSampleは今回の実行環境で48byteだった。大きなサンプル/差分/偏差配列の繰り返し生成はGC負担になる。Windows .NETでは85,000byte以上のオブジェクトがLOHに入り、Gen2回収の対象になる。[MicrosoftのLOH解説](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/large-object-heap)参照。これを「必ず10秒ちょうどで起きる閾値」とはしない。

## 計測結果

[再現プログラム・生ログ](diagnostics/performance-2026-11-01/README.md)を保存した。macOS 14.6.1 ARM64、.NET 10.0.14、Workstation GC、8論理CPU。M6のReleaseアセンブリを参照し、本体ソースは変更していない。Windows XInput APIとWPFは使用していない。

| 同上 | 10秒 | 4.35MiB | 3.64ms |
| 同上 | 30秒 | 13.38MiB | 4.53ms |

### 前回の検証からの修正

M6の仮想300秒試験は256段階の単純波形だけを使い、UIを含まず、XInput相当も100更新/秒だった。記録済みの累積割当は1k系列で39.79GiB、8k系列で290.85GiB。これをp95<100ms・ライブヒープ安定だけで十分と評価した点を修正する。CPUの平均や常駐メモリだけでなく、割当速度、GC停止、UI処理、入力→表示の遅延を受入対象とする。

## 改善後の責務と更新契約

```text
入力取得（選択したAPI、既存の観測規則）
  ├─ epoch付き最新位置の小さな公開状態 → UI位置を最大60Hzで取得
  └─ bounded観測キュー → 単一writerの30秒解析窓
                             ├─ 最新30秒の正確な統計・推定 → 10Hz
                             └─ 幅に応じた描画点と境界 → 最大10Hz
UI: 新しい位置だけ更新 / 新しい解析世代だけ数値更新 / 新しい描画世代だけ波形更新
```

`ApplicationSnapshot`全体の参照変更だけで全UIをdirtyにしない。`Epoch`、`PositionRevision`、`AnalysisRevision`、`HistoryRevision`、`WindowEndTicks`を区別する。描画要求にはサイズ/DPI由来の`RenderConfigRevision`も含める。判定はrevision単体でなく`(Epoch, Revision)`の組で行い、epoch変更/切断時に旧キャッシュを破棄する。キャッシュは各軸の最新Geometryと現在の表示設定の静的資源に限定し、世代ごとに蓄積しない。履歴がなくても時刻による期限切れは進める。無受信時にも最新30秒窓の統計が期限切れになる意味を保つ。

UIへ生サンプルごとのDispatcher処理を投入しない。最新1件を取り出すmailboxとし、遅れた描画要求は最新へ統合する。解析が遅い場合は解析結果の時刻と遅れを表示し、入力スレッドやUIを待機させない。

### R1: 計測経路と不要なUI更新の除去

- UI位置更新は最大60Hz。統計・推定・件数/詳細は新しいAnalysisRevision時の最大10Hz、診断/年齢表示は5〜10Hzとする。文字列は必要な頻度で作成し、変化したTextBlockだけ設定する。閉じた詳細は開くとき、または可視中の新世代時に生成する。
- HistoryPlot.Setは新しいHistoryRevision/WindowEnd/epoch/接続状態/サイズ/DPI時だけdirtyにする。同じ窓を約6回再描画していた経路を除く。外部要因でOnRenderが呼ばれた場合も、既存の描画資源を再使用する。
- 背景/グリッド/目盛/見出しと波形/平均/帯を分けてキャッシュする。Brush/Pen/Typeface/FormattedTextを描画ごとに作らない。静的資源はサイズ/DPI/テーマ変更で再構築し、凍結可能な共有資源をFreezeする。
- 波形は連続区間ごとにfigureを分けたStreamGeometryへまとめ、最大10Hzで再構築する。OnRenderはキャッシュ済みGeometry/Drawingを描く。UI作業が予算を超える場合は座標生成をworkerで行い、WPF資源は生成/Freeze/所有のルールを守って渡す。
- グラフが非表示なら幾何生成を休止し、再表示時は最新1件から再開する。統計と入力記録は継続する。
- 変更前後のUI tick/OnRender回数・時間、生成Geometry数、実際の点数、Dispatcher遅延を計測できるようにする。ログは上限付き集計にし、観測ごとに文字列ログを生成しない。

WPFの資源再利用方針は[2D描画の性能指針](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)、[Freezable](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/freezable-objects-overview)に基づく。StreamGeometryを使うだけで性能合格とはせず、実測で判断する。

### R2: 全件一時配列の除去と処理予算

- AxisWindowは既存Snapshotを正しさ比較用として残し、製品解析にはworker内だけ有効な読み取りviewを提供する。固定上限のリング/再利用領域を走査し、毎100msの全サンプルimmutableコピーを廃止する。保持点と時刻の順序、同tick、T-30境界、continuity、上限を保つ。
- Jitterは値/偏差の一時配列を作らず、同じ窓viewを必要な回数だけ走査する参照互換計算へ変える。単一のスカラー集計結果だけを公開する。
- modalの参照互換経路は、再利用Dictionaryの各バケットに件数と補償和を保持し、List全保存、勝者配列、Sortを除く。最多件数・同率・最小バケット選択を単一走査で決める。数値・表示の一致を試験する。
- 既存のstateless推定器が差分spanを必要とする場合は、解析worker所有のscratchを再使用する。推定器は呼出し後にspan参照を保持しない。UIへscratch/プール返却済み配列を渡さない。
- 最新1秒レートはtimestampの順序を利用して範囲/先頭/末尾/件数を求め、ToArrayを除く。現行の `(n-1)/(last-first)` と同tick時の意味を維持する。
- 最新位置の公開を重い解析完了から分離する。選択中のsourceの小さなepoch付き最新状態をatomic公開し、部分軸は最後の値/時刻を保持する。解析へサンプルを複製しない。キュー破棄がある場合、現在点と統計の対象が異なることを欠落表示で分かるようにする。
- workerは入力消費、期限切れ、解析、描画縮約の時間とキュー深度/最古待ち時間を記録する。前の計算が終わらない場合は同種の次要求を統合し、無制限にtaskを積まない。epoch変更/停止を優先し、長い走査は区切りで取消を確認する。
- 描画点は統計とは別の小さなimmutable出力だけを公開する。`AcquisitionTruncated`と`ProjectionTruncated`を分離し、描画点数制限を「30秒の取得データが欠落した」と誤表示しない。

R2は全走査の回数と割当を減らす段階であり、O(N)を完全には除かない。R3までの測定結果と残るコストを必ず残す。

### R3: 30秒解析と描画集計の増分化

**震え3指標**: 256点程度の固定長ブロックを持つ窓を用い、ブロックごとにCount/Mean/M2/Min/Maxを保持する。完了ブロックは集計木で結合し、先頭の部分失効ブロックと末尾の未完了ブロックを合わせる。集計は以下の結合式を使い、全値/全偏差配列を生成しない。

```text
N = NA + NB
δ = MeanB - MeanA
Mean = MeanA + δ * NB / N
M2 = M2A + M2B + δ² * NA * NB / N
StdDev = sqrt(M2 / N)
MaxDeviation = max(abs(Min - Mean), abs(Max - Mean))
```

式は実装時に乗算前に浮動小数へ変換し、整数のNA*NBのoverflowを避ける。空ブロックは単位元として扱う。先頭部分だけは残った最大255点程度を再集計して期限切れを正確に適用する。末尾追加はWelford等の安定な更新、完了ブロックの結合は木で行い、長時間のadd/remove差し引きによる分散の桁落ちを避ける。異常な負分散を無条件に0として隠さず、丸め誤差の許容範囲と再構築/診断を定義する。

**最頻差分**: `IStepEstimator`の参照経路を保ち、オプションの増分session契約を追加する。sessionはepoch/方式設定に束縛し、解析workerだけが追加/期限切れ/読出しを行う。

- 連続する有効な2点から作ったedgeに両端のsequence/timestampを保持する。いずれかの端が窓外になったとき除去する。窓内最初の点の前方edgeを残さない。
- バケットkeyは現行の `floor(delta/q + 0.5)`、q=1e-7、正規化/除外条件も維持する。バケットごとにCountと補償和を保持し、追加/除去で更新する。0件のバケットは除去する。
- 件数降順・key昇順の順位構造で最多バケットを取得し、同じ最多件数のバケット数からTieを判定する。最大件数が期限切れで減った場合も正しく次の勝者へ移る。1更新の目安はO(log K)、Kは現在有効なバケット数。全差分ListやそのSortを持たない。
- 選択バケットの平均差分をStepとし、段階数/bit/小数1桁四捨五入は既存共通処理を使用する。参考値件数、ExcludedCount、割合、同率時の最小keyを保つ。
- 無効値、パース失敗、既知のキュー欠落、epoch変更を跨ぐedgeを生成しない。同tick、今回の別Report IDに軸がないこと、XInput packet番号の非連番だけでは、隣接する有効観測の連続性を切らない。[XInputの追加修正](12-xinput-observed-step-fix.md)に従う。入力が来なくても時刻によるサンプルとedgeの期限切れを進める。
- 方式/設定変更時の新sessionは、現在窓から予算付きで再構築する。構築中は推定を「再計算中」とし、新しい方式名で旧結果を表示しない。統計窓自体は保持し、古いsessionからの遅延結果は方式revision/epochで棄却する。
- 増分未対応の将来の推定器にはR2のscratch付き参照経路を提供し、方式別の処理時間/遅れを診断する。方式を黙って変更しない。

**描画**: first/min/max/lastと連続区間を保持する時間ブロックを追加/期限切れ時に更新する。時間バケットは絶対単調時刻に固定し、表示窓が100ms進むたびに全サンプルを再分類しない。窓端の部分ブロックだけ境界を再評価する。サイズ/DPIの新要求は最新へ統合し、通常は全窓走査をせず集計から幅に必要な点を取り出す。

描画バケット数は表示幅から決め、最大1024、通常のfirst/min/max/lastは最大4096点/軸を目安とする。多数の連続区間がある場合も全体8192点/軸を上限とし、上限超過時は全時間バケットをさらに縮約し、窓内の最古・最新点を保持する。表示期間の古い側を捨てず、点の省略だけを別flagで示す。[波形保持修正](11-history-coverage-fix.md)参照。省略で欠測区間を直線で結ばない。間引き結果を統計入力に戻さない。表示generation/epochが古い遅延結果は破棄する。

## 維持する計測仕様

最新30秒、4軸、受信サンプル等重み、母標準偏差/平均/平均からの最大絶対偏差、q、最頻差分、bit換算、元整数・正規化を維持する。XInputの同じpacketを複製せず、HIDの届かなかった軸を補完しない。現在点の表示用最終値保持と、統計へのサンプル追加を分ける。表示の更新抑制は取得の間引きではない。

数値の参照比較には旧Snapshot/計算器を使う。窓境界、古い極値/最頻値の期限切れ、一定値、微小振動、移動、大量ゼロ、同率、片軸無効、30秒無受信を固定fixtureと生成系列で比較する。初期目標は平均・最大偏差の絶対誤差1e-10以下、標準偏差1e-9以下（極小値は相対誤差も記録）。基本step・bitは誤差を定量化し、既知fixtureと丸め境界の表示文字列が一致しない場合は不合格とする。許容誤差の変更は理由を設計に残す。

## R4: Windowsでの性能受入

同一のWindows 11 x64実機・Release配布版・通常モードで変更前後を比較する。OS/CPU/RAM/GPU/描画tier/DPI、API呼出し/状態更新、軸件数、GC設定、プロセスCPUとUIスレッドCPUを記録する。今回の報告条件を最優先にする。

- XInput実機・通常・目標1,000 API呼出し/秒。静止、微振動、ゆっくり移動、高速操作、ボタンだけの更新、状態不変を含む。実際のAPI/状態更新レートは別々に記録する。
- 取得・解析・WPFを同時に動かす実時間5分試験。1/5/10/20/30/60/300秒の区間を比較する。Windows上の合成入力でも1k/8kを実時間再生し、多種類差分・欠落・部分軸・上限を含める。
- 30秒以後の10分以上の定常運転と、リセット/方式切替/抜き差し/終了/スクロール/移動/リサイズ/150%/200%DPIを確認する。
- グラフ表示/非表示、位置だけ、解析を固定fixtureに置換した表示だけ、解析付きの各条件を診断用に比較し、UIと解析/GCの寄与を切り分ける。切り分け用条件を製品の合格結果に代用しない。

次は**改善後の目標**で、今回達成した値ではない。基準Windows実機を記録して判定する。

| 指標 | 1k観測/秒の目標 | 8k合成入力の目標 |
| --- | --- | --- |
| UI tick＋アプリOnRenderのUI占有（各UI周期、二重計上なし） | p95<8ms、p99<16ms | 同左 |
| 操作を処理するまでのDispatcher待ち | p95<50ms、p99<100ms | 同左 |
| 観測時刻→現在点反映（制御済み合成入力） | p95<50ms | p95<50ms |
| 4軸の解析・描画点生成 | p95<20ms、p99<50ms | p95<50ms、p99<100ms |
| 定常時のプロセス割当量（GUI/取得/解析込み） | 10MiB/秒以下 | 40MiB/秒以下 |
| GC停止（1回、定常時） | p99<10ms、全停止時間比5%未満 | 同左 |
| キュー | 通常負荷の既知破棄0、解析要求/描画要求の滞留が時間とともに増えない | 同左。意図的飽和時は欠落表示と操作応答を確認 |
| ライブメモリ | 30秒窓充足後に増加傾向が収束、定常5区間で保持量と未処理件数が安定 | 同左 |

現在点の反映時刻はその世代を最初にOnRender等で描画提出した時刻として測り、観測元の単調クロックと照合する。画面発光までを測る場合は別の外部計測として記録する。

CPUは全CPU比だけでなく1コア換算/スレッド別で記録する。計測ログ自体の負荷を確認し、詳細トレース有無の両方で比較する。p95だけで合格にせず、最大停止/100ms超イベントも原因とともに残す。Dispatcher待ち・GC・解析・描画の時系列を合わせて評価する。目標未達なら担当処理を特定してR1〜R3へ戻し、「メモリが一定」を理由に完了としない。

.NETの割当/GC/CPUは[dotnet-counters](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters)、呼出しスタック/GC停止は[dotnet-trace](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace)等で取得する。WPFのレイアウト/レンダリングとUIスレッドはVisual StudioのプロファイラーまたはWindows ETWで確認する。ツールのバージョン・取得設定も結果に残す。

## 2026-11-02追加変更後の再検証

[追加変更後の試験記録](15-verification-2026-11-02.md)に現行コードの結果を記載した。機能試験161ケースは合格。300秒相当・12条件で30秒波形の期間短縮は0秒だが、8kHzで全観測を別continuityにする条件は解析p99約159ms・最大約193ms、生存ヒープ約566MiBとなり目標未達。60秒試験の過去の合格値や小さなp95を根拠に、この条件を性能合格としない。

次の性能調査では、欠測区切りごとの投影segment／dictionary／linked listの保持・割当とGCを切り分ける。compactな値型格納や再利用を候補とし、端点・極値・欠測境界の保持を回帰試験で守る。仮想時間を圧縮したGCの影響と、Windows実時間の解析／WPF同時実行を分けて測定する。通常条件の合格だけでこの残課題を閉じない。
